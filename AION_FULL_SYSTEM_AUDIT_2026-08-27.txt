--- NEW FINDING: CORS rejects Vite's fallback dev ports ---
SEVERITY: P2 (dev-experience / diagnosability, not a security or
  production-mission blocker)
ROOT CAUSE: ALLOWED_ORIGINS hardcoded only localhost:5173/4173.
  Vite silently falls back to 5174, 5175, ... when a lower port is
  occupied (confirmed: this is exactly what happened -- port 5174 was
  in use this session). A CORS-rejected request surfaces to browser JS
  only as the generic "Failed to fetch" (browsers deliberately hide the
  specific CORS reason from catch code), which is indistinguishable
  from a real network/backend outage without opening browser devtools'
  network tab specifically.
STATUS: FIXED this pass.
FIX: app/api.py -- allow_origin_regex now matches
  https?://(localhost|127.0.0.1):<any port>, in addition to the
  existing Firebase-preview-channel pattern (combined into one regex,
  Starlette only accepts one). Safe specifically for localhost: the
  Origin header cannot be spoofed cross-origin, so only a page actually
  running on the same machine can ever present it -- a fundamentally
  different trust boundary than a public web origin. Production origins
  and the owner-token requirement for mutations are both unaffected.
REGRESSION TESTS: tests/test_api.py::test_vite_fallback_port_is_allowed
  (5174/5175/3000/8080 all correctly get CORS headers) and
  test_localhost_pattern_does_not_grant_a_remote_lookalike_origin
  (negative control: a domain merely containing "localhost", or a real
  LAN IP, is correctly still rejected).
COMMIT: e76cb9f
VERIFICATION: 6/6 CORS-specific tests pass; full backend suite 562
  passed / 2 skipped / 0 failed (up from 560, +2 new tests); zero
  regressions.

--- INVESTIGATED, NOT A BUG: POST /monitors/run-due -> 401 ---
The route is owner-token-gated by design
(dependencies=[Depends(require_owner)]) -- confirmed by direct source
read, app/api.py line ~807. grepped the ENTIRE repository (source,
docs, CI workflows, deploy scripts) for any Cloud Scheduler job
definition, IAM binding, or OIDC configuration targeting this route:
NONE EXISTS ANYWHERE. No scheduler was ever actually provisioned for
this project. The 401 observed in the Cloud Run logs is the endpoint
correctly refusing an unauthenticated caller -- almost certainly a
manual/ad-hoc call (curl, browser, or a misconfigured attempt) made
without the owner token, not a broken authentication mechanism.
ROOT CAUSE OF THE UNDERLYING GAP: no Cloud Scheduler job (or other
authenticated caller) has ever been set up for this endpoint. This is
a missing piece of INFRASTRUCTURE, not a code defect. Per this
project's own standing rule ("do not solve authentication failures by
making protected endpoints public"), this was NOT weakened. If the
owner wants scheduled monitor execution working end-to-end, the real
next step is a deliberate infrastructure decision: either (a) a Cloud
Scheduler job configured with the owner token as a custom header
(workable but means a long-lived secret sits in Scheduler job config),
or (b) extending require_owner to also accept Cloud Run's own OIDC
service-to-service token for this one route specifically (a real,
scoped auth-model change, not something to do silently in a general
audit pass). Flagging for an explicit owner decision, not implemented.
STATUS: no code change made. Correctly working as designed.
